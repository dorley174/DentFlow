## Что покрывают тесты

- Запись через публичный API → пациент → CRM → кабинет → перенос → старый слот свободен → другая запись.
- Повторные запросы и неизменность idempotency key; конфликт при частичном и полном пересечении интервала.
- Ручная запись существующего и нового пациента, защита от повторного создания.
- Guided chat создаёт запись, запрашивает согласие, передаёт диалог сотруднику.
- Изоляция tenant, запрет доступа Patient к кабинету, ограничение Doctor, отсутствие глобального клинического доступа Super Admin.
- Нет объединения гостей по одинаковому телефону; сессии пациента и сотрудника не смешиваются.
- Создание клиники, настройка врача/услуг/смен, изменение прайса, проверка будущих визитов при правке смены.
- Dev reset восстанавливает только Smile Avenue; production-конфигурация отклоняет опасные сочетания флагов.
- Автоматизации и защита от повторного создания; отзыв маркетинга отменяет реактивацию, сохраняя разрешённые сервисные уведомления.
- Одноразовый Telegram link, истечение исходной сессии, запрет чужого tenant, повторные update и устаревшие кнопки.
- Telegram использует общий сервис записи; сетевой сбой не превращается в ложное delivered.
- Внешние AI по умолчанию отключены; имя, телефон, медицинский или неизвестный текст не пересекают внешнюю границу.
- Публично безопасные сообщения при ошибке провайдера; контракты Yandex/GigaChat проверены синтетическими транспортными ответами.

## Что не проверено в этой среде

**Настоящий многопользовательский PostgreSQL server, Docker Engine и браузерный preview здесь недоступны.** Поэтому нельзя считать выполненными запуск контейнеров на вашем хосте, браузерный end-to-end тест, визуальную проверку desktop/mobile и конкурентный тест двух независимых подключений PostgreSQL.

PGlite исполняет PostgreSQL SQL и проверяет схему/constraints, но не заменяет проверку драйвера psycopg, серверных соединений и конкуренции. `test_postgres_concurrency.py` намеренно пропущен на SQLite; в GitHub CI он запускается с настоящим PostgreSQL 17.

Реальные токены Telegram/LLM не предоставлялись; живые внешние API, биллинг, TLS сертификаты целевого сервера, DNS, восстановление на отдельной VM, реальная МИС и платёжные системы не тестировались. Исследование нормативных источников не является юридическим аудитом.

## Как повторить Python-проверки

Для разработчика: Python 3.12, отдельное виртуальное окружение и тестовая БД. Из папки backend:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
```

На Windows вместо `source` используйте `.venv\Scripts\Activate.ps1`. При отсутствии DATABASE_URL conftest выберет отдельный файл `.test-dentflow.db`. Тесты **очищают тестовую схему**, поэтому никогда не передавайте рабочую БД. Дополнительный guard допускает PostgreSQL только с именем `dentflow_test`.

Для настоящего PostgreSQL заранее создайте отдельную пустую БД `dentflow_test` и укажите её DATABASE_URL. В GitHub workflow эта БД создаётся как временный сервис. Test role должен иметь возможность установить btree_gist в тестовой БД.

## Frontend

Из папки frontend:

```bash
npm ci
npm run typecheck
npm run build
```

В локальной разработке backend должен быть доступен на 127.0.0.1:8000 либо через BACKEND_URL. В Docker этот адрес задаётся на этапе сборки, а внешний доступ всегда проходит через Nginx gateway. Для production установка dev-зависимостей в runtime не нужна: используется standalone output.

## CI и приёмка после развёртывания

`.github/workflows/ci.yml` содержит три независимых задания: backend + PostgreSQL, frontend и полный Compose build/start с HTTP health. Файл workflow подготовлен, но его запуск на вашем GitHub account ещё не выполнялся. Не объявляйте CI зелёным до фактического результата Actions.

После первого запуска повторите все шаги DEV_STAND.md в двух браузерных сессиях. Отдельно проверьте мобильную ширину, модальные окна, длинные названия услуг, отмену и повтор отправки при потере сети. Затем протестируйте свои токены, ограничение доступов и восстановление из резервной копии. Зафиксируйте commit, дату, окружение и обнаруженные ошибки.

В тестовом выводе присутствует предупреждение совместимости Starlette о будущем переходе с httpx на httpx2. Текущий suite проходит; при обновлении тестового транспорта проверяйте зависимости и поведение cookies заново. Это предупреждение не отменяет перечисленных ограничений проверки среды.
