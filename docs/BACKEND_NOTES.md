# Backend: реализованный контракт

Дата сборки: 5 ноября 2026 года. Backend — модульный монолит FastAPI / SQLAlchemy 2. Рабочая база данных — PostgreSQL; SQLite разрешена только при `APP_ENV=test` для быстрых локальных проверок. Все суммы хранятся целыми числами в копейках. Даты API содержат часовой пояс. Демонстрационная клиника использует `Europe/Moscow`.

## Сквозной сценарий

1. `GET /api/public/clinics/smile-avenue` возвращает каталог и выставляет отдельную HttpOnly visitor cookie.
2. `GET .../slots?service_id=...&doctor_id=...&branch_id=...&date=YYYY-MM-DD` рассчитывает слоты по рабочим часам, перерывам и занятым интервалам.
3. `POST .../appointments` принимает выбранный интервал, имя, телефон, отдельные согласия и `idempotency_key`.
4. В одной транзакции появляются пациент, запись, лид CRM, уведомление и запись аудита. У пациента той же доказанной сессии используется существующий профиль. Совпадение имени или телефона не объединяет профили.
5. Администратор видит запись через `/api/admin/bootstrap` и может перенести её. Новый интервал проверяется; старый освобождается после успешной транзакции.
6. В веб-чате тот же сценарий проходит через последовательные кнопки: услуга, филиал, врач, свободное время, имя/телефон, явное согласие. Это реальные операции backend.

Защита записи: Pydantic-валидация, проверка tenant, блокировка строки врача PostgreSQL `SELECT FOR UPDATE`, повторная проверка пересечений и дополнительное ограничение `EXCLUDE USING gist` в миграции. Интервалы полуоткрытые: окончание одного визита может совпадать с началом другого. Ключ идемпотентности привязан к идентичности вызывающего.

## Авторизация и роли

Серверные непрозрачные сессии: токен в HttpOnly cookie, SHA-256 токена в БД, ограниченный срок действия. Пароли — PBKDF2-HMAC-SHA256 с индивидуальной солью и 600 000 итераций. Изменение пароля, роли или активности сотрудника отзывает его сессии.

| Роль | Разрешения |
|---|---|
| `super_admin` | Клиники, тарифы, агрегаты, коммерческие заявки; нет клинического bootstrap |
| `owner` | Полный кабинет своей клиники, включая сотрудников |
| `manager` | Каталог, расписания, настройки, автоматизации и ежедневная работа |
| `administrator` | Записи, CRM, задачи и диалоги; каталог доступен на чтение |
| `doctor` | Собственные записи, связанные с ними пациенты, собственное расписание; без CRM и диалогов |
| `patient` | Только собственные записи и данные через публичный интерфейс |

При входе под аккаунтом пациента visitor cookie меняется: профили предыдущего аккаунта или анонимного гостя не объединяются автоматически. При выходе отзываются эта capability и её незавершённые коды привязки канала. Вход администратором сохраняет независимую гостевую сессию для проверки Dev Stand в одном браузере.

Для небезопасных HTTP-методов нужны `Content-Type: application/json`, `X-Requested-With: DentFlow`; при наличии `Origin` он должен входить в точный список `ALLOWED_ORIGINS`. В production включаются Secure cookies, обязательный Redis для общего rate limit, HTTPS origins и уникальный `SECRET_KEY`.

## Административные данные

`GET /api/admin/bootstrap` возвращает `user`, `tenant`, `branches`, `doctors`, `services`, `patients`, `appointments`, `leads`, `conversations`, `tasks`, `notifications`, `automation_rules`, `integrations`, `ai_settings`, `staff`, `schedules`, `metrics`, `audit_logs`, `subscription`. Результат ограничивается ролью.

`GET /api/admin/{resource}` возвращает `{items: [...]}`. `POST` и `PATCH /{id}` для каталогов возвращают `{item: ...}`. Для записей результат — `{appointment: ...}`. Поддерживаемые редактируемые ресурсы: `branches`, `doctors`, `services`, `schedules`, `leads`, `tasks`, `employees`, `automation_rules`. Записи и диалоги имеют отдельные маршруты.

`PATCH /api/admin/settings` принимает `{tenant: {...}, ai_settings: {...}}`. Секреты не принимаются через этот маршрут. Имена, цены, цвета, рабочие часы, назначения услуг врачам и настройки сохраняются в БД. Изменение расписания не может скрыть уже созданные будущие визиты: сначала надо перенести или отменить их.

Лимит активных филиалов тарифа проверяется при создании и повторном включении филиала под блокировкой tenant. Лимит внешних AI-классификаций проверяется перед вызовом за текущий месяц; это предварительный лимит, а не гарантированный биллинг провайдера при одновременных запросах.

## Состояния

- Запись: `scheduled`, `confirmed`, `completed`, `cancelled`, `no_show`.
- Задача: `open`, `in_progress`, `done`.
- Диалог: `mode=ai|human`; сообщения `patient|assistant|staff`.
- CRM: «Новое обращение», «Не обработано», «В работе», «Консультация», «Предложено время», «Записан», «Подтверждён», «Посетил», «Завершено», «Потерян».

Карточка пациента вычисляет число завершённых визитов, дату последнего визита и сегмент по фактическим записям. Финансовые показатели — стоимость записей по прайсу, а не подтверждённые кассовые поступления.

## AI и Telegram

Режим по умолчанию — `demo`: детерминированный административный движок без внешних запросов. Он читает реальный каталог и расписание, выполняет запись и передачу сотруднику. Медицинские вопросы переводятся человеку; нет диагностики и назначения лечения.

Опциональная LLM классифицирует только короткие фразы из закрытого административного словаря. История, произвольный текст, телефоны, имена и сведения о здоровье внешнему провайдеру не передаются. Цены, время и подтверждения формирует backend. При ошибке внешнего сервиса сохраняется локальный сценарий. Реальные tokens сохраняются; неизвестная стоимость внешнего API — `null`, а не нулевая «бесплатная» стоимость.

Настраиваемое приветствие применяется к новым диалогам; административная база знаний используется в ответах об адресе, парковке, оплате и правилах визита. Ответы сотрудника требуют явного перехвата диалога. Для Telegram ответ сохраняется в durable outbox; это не гарантия, что внешний Telegram уже принял сообщение.

## Автоматизации

`run_automations(db, tenant_id, now=None)` вызывается worker и вручную через API. Изменения коммитит вызывающий. Есть блокировка tenant и уникальные ключи событий для защиты от повторного создания.

Реализованы напоминания до визита, задачи при отсутствии ответа, запрос обратной связи, реактивация при двух разрешениях (`notifications_enabled` и `marketing_enabled`). Отзыв маркетингового согласия отменяет ожидающую реактивацию, не отключая административные напоминания. Лист ожидания в этой версии — управляемая сотрудником задача; автоматического назначения освободившегося слота нет.

В Dev Stand можно ускорить проверку правил через `advance_minutes` и симулятор событий. Реальное время сервера и даты записей при этом не меняются.

## Данные пациента

- `GET .../notifications` — собственные уведомления.
- `GET/PATCH .../consents` — согласия на уведомления и маркетинг.
- `GET .../my-data` — JSON-выгрузка своего профиля, записей, согласий и переписки.
- `POST .../delete-my-data` с `confirmation=DELETE MY DATA` — официальный запрос оператору на удаление, отключающий коммуникации и создающий задачу сотруднику. Не обещает мгновенного стирания записей, для которых может действовать обязательный срок хранения. Порядок окончательного удаления утверждает оператор.

## Dev Stand и тесты

Seed содержит Smile Avenue: 2 филиала, 5 врачей, 12 услуг, 30 вымышленных пациентов, 20 будущих записей, CRM, диалоги и задачи. Дополнительный tenant «Аврора Дент» нужен для проверки изоляции.

Seed/reset отказываются работать в production и с неизвестным именем БД. В `APP_ENV=test` PostgreSQL разрешён только с именем `dentflow_test`; тестовый запуск также проверяет имя до удаления таблиц. Сброс доступен только Super Admin при `ENABLE_DEV_TOOLS=true`, требует `RESET SMILE AVENUE`, затрагивает только демонстрационную Smile Avenue и отзывает её прежние учётные записи. Клиника «Аврора Дент» сохраняется.

Тесты API выполняются in-process без сетевого сервера. Отдельный concurrency-тест требует настоящего PostgreSQL и намеренно пропускается на SQLite. Это ограничение нельзя считать доказанной проверкой PostgreSQL row locks в локальной среде.
