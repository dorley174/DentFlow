# Развёртывание DentFlow: инструкция для новичка

**Сначала запустите проект на своём компьютере.** После проверки записи и кабинета можно вынести закрытый Dev Stand на сервер. Контур для реальных клиник создаётся отдельно, без переноса демонстрационных пациентов.

Архив содержит исходный код. Само наличие проекта на GitHub не запускает сайт. **GitHub хранит код; Docker запускает приложение; сервер делает его доступным по сети.** GitHub Pages не подходит этому проекту: здесь нужен работающий Python backend и PostgreSQL.

## 1. Что вы получили

| Файл / папка | Для чего нужен |
|---|---|
| START_HERE.html | Эта инструкция в удобном виде. Открывается без сервера. |
| README.md | Краткий старт и карта проекта |
| frontend | Сайт и кабинеты на Next.js / React |
| backend | API, запись, CRM, авторизация, чат, бот и фоновые задачи |
| compose.yaml | Локальный тестовый стенд |
| compose.production.yaml | Отдельный контур реальных клиник |
| .env.example | Образец локальных настроек; настоящая конфигурация создаётся как .env |
| .env.production.example | Образец production; настоящая конфигурация — .env.production |
| start.ps1 / start.sh | Первый запуск Windows / macOS / Linux |
| docs | Техническая документация и проверяемые ограничения |
| .github/workflows | Автоматические проверки и необязательное ручное развёртывание |

В тестовой клинике только вымышленные люди и цены. В архив не включены действующие API-ключи, реальные пациентские данные, установленные зависимости или локальные секреты.

## 2. Подготовьте компьютер

Нужны современная Windows / macOS / Linux, интернет для первой сборки и Docker. Для комфортной сборки проекта планируйте не менее 8 ГБ памяти на компьютере и несколько десятков гигабайт свободного диска. Это ориентир для проекта, а не гарантированный минимум для любой системы.

### Windows

1. Скачайте установщик по [официальной инструкции Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/).
2. Установите Docker Desktop с Linux containers / WSL 2. Если установка требует обновить WSL или перезагрузить компьютер, выполните указания установщика.
3. Откройте Docker Desktop и дождитесь готовности движка. Одной установки без запуска недостаточно.
4. Распакуйте ZIP, например в `C:\Projects\dentflow`. Не запускайте файлы прямо внутри окна архива.
5. Откройте папку, в которой лежит `compose.yaml`. В адресной строке Проводника наберите `powershell` и нажмите Enter.
6. Проверьте Docker:

```powershell
docker --version
docker compose version
```

Обе команды должны показать версии. Затем:

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
```

Параметр ExecutionPolicy относится к этому отдельному процессу PowerShell. Он не меняет системную политику постоянно. Запускайте скрипт только из полученной папки проекта.

### macOS

1. Откройте [официальную страницу Docker Desktop для Mac](https://docs.docker.com/desktop/setup/install/mac-install/).
2. Выберите установщик под процессор: Apple silicon для M1/M2/M3/M4 и последующих Apple chips; Intel — для Intel Mac. Тип можно посмотреть в меню Apple → «Об этом Mac».
3. Установите Docker Desktop в Applications и откройте его.
4. Распакуйте ZIP. Откройте приложение Terminal.
5. Наберите `cd ` с пробелом, перетащите папку `dentflow` в Terminal и нажмите Enter. Так не нужно вручную вводить путь.
6. Выполните:

```bash
docker compose version
bash start.sh
```

### Linux

Установите Docker Engine и Compose plugin по [официальной инструкции для вашего дистрибутива](https://docs.docker.com/engine/install/). Затем перейдите в папку проекта и выполните `bash start.sh`. Для Ubuntu серверный вариант описан ниже. Если пользователь не имеет доступа к Docker, настройте разрешения по официальной инструкции или используйте sudo осознанно; членство в группе docker даёт высокие права на хосте.

### Что происходит при запуске

Скрипт создаёт `.env` со случайными локальными секретами. Затем Docker скачивает образы, устанавливает зависимости, собирает интерфейс, запускает PostgreSQL и Redis, применяет миграцию и наполняет Smile Avenue. Первый запуск обычно заметно дольше последующих; время зависит от компьютера и сети.

Нормальные сообщения: `Building`, `Downloading`, `Running`, `Healthy`. Не закрывайте Docker Desktop. Если команда завершилась ошибкой, сначала прочитайте раздел 13, а не запускайте удаление томов.

## 3. Откройте проект и выполните первый тест

После сообщения `DentFlow запущен` откройте в браузере:

**http://localhost:8080**

`localhost` — ваш компьютер. Эта ссылка не открывает проект на телефоне или чужом компьютере. По умолчанию порт привязан к 127.0.0.1, поэтому тестовый стенд не опубликован в интернете.

Проверка в двух окнах:

1. В обычном окне откройте `/login` и войдите как `owner@dentflow.local` с паролем `Owner-Demo-2026!`.
2. Откройте кабинет клиники. Владелец видит также справочники и настройки; обычный администратор имеет меньше прав.
3. Откройте окно инкогнито и адрес `http://localhost:8080/clinic/smile-avenue`. Инкогнито отделяет сессию пациента от сотрудника.
4. Выберите услугу, филиал, врача, будущую дату и свободное время.
5. Введите вымышленные имя и телефон, например «Тестовый Пациент» и `+70000000001`. Подтвердите отдельное согласие для записи. Напоминания — отдельный выбор.
6. Нажмите подтверждение и дождитесь сообщения об успешном сохранении.
7. Вернитесь в кабинет и обновите расписание. Перейдите именно на выбранную дату: новые данные могут быть на завтра, а не сегодня.
8. Найдите пациента и CRM-лид. Перенесите визит на другой свободный интервал.
9. В окне пациента откройте «Мои записи» и обновите данные. Убедитесь, что время изменилось.

Затем повторите запись **через чат**: «Записаться» → услуга → филиал → врач → время → имя и телефон → отдельное подтверждение согласия. Это проверяет другой интерфейс к той же БД. Подробные проверки, роли и симулятор описаны в DEV_STAND.md.

Публичный чат на главной странице DentFlow — отдельный иллюстративный пример. Он прямо сообщает, что запись не создаётся. Настоящий тест выполняется в Smile Avenue.

## 4. Остановка, повторный запуск, данные

Откройте терминал в папке проекта.

```bash
docker compose stop
```

Это останавливает приложение и сохраняет данные. Следующий запуск:

```bash
docker compose start
```

После изменения кода или настроек:

```bash
docker compose up -d --build --wait --wait-timeout 300
```

Состояние контейнеров:

```bash
docker compose ps
```

Данные хранятся в Docker volumes. **`docker compose down -v` удаляет тома и базу.** Это не обычная команда остановки. Для возврата исходной Smile Avenue войдите под Super Admin и используйте защищённую кнопку сброса с подтверждением.

## 5. Загрузите проект в GitHub

### Вариант А: GitHub Desktop

Для первого репозитория проще использовать [GitHub Desktop](https://desktop.github.com/).

1. Создайте аккаунт GitHub, установите GitHub Desktop и войдите.
2. В Desktop выберите **File → Add Local Repository** и папку `dentflow`.
3. Если написано, что папка ещё не Git repository, нажмите предложенное **Create a repository here**. Проверьте итоговый путь: это должна быть существующая папка с `compose.yaml`, а не вложенная `dentflow/dentflow`.
4. В списке изменений должны быть `frontend`, `backend`, `docs`, `.github`, `compose.yaml` и примеры `.env`. Настоящих `.env`, `.env.production`, файлов БД и backups быть не должно.
5. Введите описание первого коммита, например `Initial DentFlow MVP`, и нажмите **Commit to main**. Если Desktop уже создал initial commit, этот шаг может быть не нужен.
6. Нажмите **Publish repository**, задайте имя `dentflow` и оставьте **Keep this code private** включённым для начала.
7. Откройте репозиторий через **Repository → View on GitHub**. Убедитесь, что README отображается, а папки проекта доступны.

Справка: [добавление существующего проекта в GitHub Desktop](https://docs.github.com/en/desktop/adding-and-cloning-repositories/adding-an-existing-project-to-github-using-github-desktop). Удалять remotes в этом новом архиве не требуется: чужой origin здесь не настроен.

### Вариант Б: Git в терминале

Подходит, если Git уже установлен и настроена авторизация. Создайте на GitHub пустой private repository без автоматически добавленного README. Замените YOUR_LOGIN на свой логин:

```bash
git init
git branch -M main
git add .
git commit -m "Initial DentFlow MVP"
git remote add origin https://github.com/YOUR_LOGIN/dentflow.git
git push -u origin main
```

Если Git попросит имя автора, задайте свои `git config user.name` и `git config user.email` в этом репозитории. Авторизация выполняется через поддерживаемый GitHub механизм; не вставляйте токен в remote URL и не сохраняйте его в `.env.example`.

### После загрузки

Откройте вкладку **Actions**. CI проверяет backend, настоящий PostgreSQL, frontend и сборку Docker. Если проверка красная, откройте конкретный job и сообщение об ошибке. Зелёный CI — важная проверка переносимости, но не замена пилота и проверки внешних сервисов.

Не загружайте на GitHub только один ZIP: тогда GitHub не сможет показать исходники и запустить приложенные workflow. Загружается именно содержимое архива.

## 6. Закрытый Dev Stand на российском сервере

Для демонстрации вне своего компьютера можно взять VM у российского провайдера, например Selectel, Yandex Cloud или VK Cloud, выбрав российский регион и подходящие условия. Ссылки и критерии выбора — MARKET_RESEARCH.md. Начальный ориентир для пилота: Ubuntu 24.04 LTS, 4 vCPU, 8 ГБ RAM и 40–60 ГБ SSD. Это оценка, а не обещание производительности.

Для новичка безопаснее оставить Dev Stand закрытым и заходить через SSH-туннель. Открывать в интернет тестовые пароли не нужно.

### Подключение к серверу

В панели провайдера создайте VM, добавьте свой SSH-ключ и узнайте IP и имя пользователя. Следующая команда вводится **на вашем компьютере**; замените значения:

```bash
ssh USER@SERVER_IP
```

При первом подключении сравните fingerprint ключа сервера с доверенным источником провайдера. После входа команды выполняются на сервере, пока вы не введёте `exit`.

### Установка Docker на чистую Ubuntu 24.04

Проверьте [актуальную официальную инструкцию](https://docs.docker.com/engine/install/ubuntu/) перед использованием. Для новой VM:

```bash
sudo apt update
sudo apt install -y ca-certificates curl git unzip python3
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

Создайте запись репозитория Docker:

```bash
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run --rm hello-world
```

Последняя команда должна завершиться приветственным сообщением Docker. Далее либо используйте sudo для Docker-команд, либо настройте доступ отдельному пользователю по официальной инструкции. Не смешивайте запуск одного проекта из разных папок и под разными Compose project names.

### Перенос файлов

Проще передать ZIP командой **на вашем компьютере**, находясь в папке с архивом:

```bash
scp DentFlow_GitHub.zip USER@SERVER_IP:~/
```

На сервере:

```bash
unzip DentFlow_GitHub.zip
cd dentflow
python3 scripts/configure.py
sudo docker compose up -d --build --wait --wait-timeout 300
```

Если вы клонируете private GitHub repository вместо копирования ZIP, используйте отдельный read-only deploy key для сервера. Не кладите личный GitHub-токен в исходники. Для ручного CD из раздела 12 нужен именно git checkout на сервере.

### Вход через SSH-туннель

Если локальная копия уже использует порт 8080, сначала остановите её командой `docker compose stop`. В новом терминале **на вашем компьютере**:

```bash
ssh -N -L 8080:127.0.0.1:8080 USER@SERVER_IP
```

Не закрывайте это окно. Откройте http://localhost:8080. Теперь браузер подключён к серверному стенду через SSH. Публичный доступ к порту 8080 остаётся закрытым. Для завершения туннеля нажмите Ctrl+C.

Домен dev.example.ru для такого способа не нужен. Если нужен общий закрытый домен для команды, настройте VPN или дополнительную проверку доступа на reverse proxy; одной страницы входа с опубликованными демопаролями недостаточно.

## 7. Отдельный production-контур

Этот раздел создаёт техническую основу для будущего пилота реальной клиники. До ввода настоящих данных пройдите проверки SECURITY.md, LEGAL_COMPLIANCE.md и ROADMAP.md. Не переносите вымышленных пациентов и тестовые учётные записи в рабочую базу.

Используйте **другую VM** и отдельные ключи. Установите Docker по предыдущему разделу. Разместите код в `/opt/dentflow`; пользователь развёртывания должен владеть этой папкой.

В папке проекта создайте конфигурацию, заменив домен на свой:

```bash
python3 scripts/configure.py --production --domain app.example.ru
```

Скрипт создаст `.env.production`, случайные DB password/SECRET_KEY и HTTPS origins. Если файл уже существует, он не перезаписывается. Откройте его локальным текстовым редактором на сервере, например `nano .env.production`, и проверьте домен. Не отправляйте этот файл в GitHub или переписку.

Запуск:

```bash
sudo docker compose --env-file .env.production -f compose.production.yaml up -d --build --wait --wait-timeout 300
```

Создаётся отдельная БД `dentflow_production`, выполняется миграция, запускается приложение. Seed демонстрационной клиники **не вызывается**. Окружение принудительно production, dev-инструменты выключены, cookie требуют HTTPS.

Создайте владельца платформы:

```bash
sudo docker compose --env-file .env.production -f compose.production.yaml exec backend python -m app.bootstrap --email owner@example.ru --name "Владелец DentFlow"
```

Введите новый уникальный пароль дважды. При вводе символы могут не отображаться — это нормально. Пароль не передаётся в командной строке и не печатается. Тестовый `super@dentflow.local` в production не создаётся.

Далее настройте HTTPS; до этого production login по обычному HTTP работать корректно не должен из-за Secure cookie.

## 8. Домен и HTTPS

### DNS

У регистратора своего домена добавьте A-запись:

| Поле | Значение |
|---|---|
| Имя | app |
| Тип | A |
| Значение | IP production-сервера |

Это свяжет `app.ВАШ-ДОМЕН.ru` с сервером. Не оставляйте `app.example.ru`: это текстовый пример. Дождитесь обновления DNS и проверьте, что он указывает на вашу VM.

### Reverse proxy

На сервере установите Nginx:

```bash
sudo apt install -y nginx
sudo cp infra/host-nginx.example.conf /etc/nginx/sites-available/dentflow
sudo nano /etc/nginx/sites-available/dentflow
```

В файле замените `app.example.ru` на свой домен. Затем:

```bash
sudo ln -s /etc/nginx/sites-available/dentflow /etc/nginx/sites-enabled/dentflow
sudo nginx -t
sudo systemctl reload nginx
```

Если ссылка уже существует, повторно создавать её не нужно. `nginx -t` должен завершиться сообщением об успешной проверке. В security group провайдера разрешите 80 и 443 для сайта, а SSH — только из доверенных сетей. PostgreSQL 5432, Redis 6379, Python 8000 и Next.js 3000 наружу не публикуются.

### Сертификат

Используйте [официальную инструкцию Certbot для Nginx](https://certbot.eff.org/instructions?ws=nginx&os=snap). На чистом Ubuntu-сервере со snap:

```bash
sudo apt install -y snapd
sudo snap install --classic certbot
sudo ln -s /snap/bin/certbot /usr/bin/certbot
sudo certbot --nginx -d app.example.ru
sudo certbot renew --dry-run
```

Замените домен. Если certbot уже установлен другим способом, не смешивайте установки: следуйте инструкции его обновления. Программа запросит рабочий email и принятие условий сертификата. Проверка renew должна пройти успешно. При необходимости выбирайте перенаправление HTTP на HTTPS.

Откройте **https://ВАШ-ДОМЕН/login**, войдите созданным владельцем, перейдите в Super Admin, создайте клинику и её владельца. Затем войдите под владельцем клиники и добавьте филиалы, услуги, врачей и смены. Для нового врача нужно явно связать услуги и создать рабочие дни — иначе свободных слотов не будет.

### Собственный домен клиники

Приложение уже обслуживает `/clinic/<slug>` на общем backend. Для домена клиники настройте DNS/HTTPS на тот же сервер, добавьте точный origin в ALLOWED_ORIGINS и в server-блоке направьте корень на страницу её slug:

```nginx
location = / {
    return 302 /clinic/my-clinic;
}
```

Остальные пути, включая `/api`, передавайте тому же gateway. Это ручная эксплуатационная настройка; поле домена в кабинете не меняет DNS автоматически. Связь с клиникой по slug всё равно проверяет backend.

## 9. Резервные копии и восстановление

Перед обновлением и регулярно в production:

```bash
bash scripts/backup.sh production
```

Если Docker доступен только с sudo, запустите `sudo bash scripts/backup.sh production`. Скрипт создаёт custom dump в `backups/production/`, не печатает секреты и не меняет данные. Локальный Dev Stand сохраняется командой `bash scripts/backup.sh devstand`.

Перенесите копию в защищённое хранилище в согласованном российском регионе. Сроки хранения, шифрование и доступ определяет оператор. Копия, лежащая только на той же VM, не защищает от её потери.

Проверить восстановление можно в **новую** БД:

```bash
bash scripts/restore.sh production backups/production/ИМЯ_КОПИИ.dump dentflow_production_restore_20261105
```

Команда не очищает рабочую базу. Она откажется использовать имя без `dentflow_production_restore_`. Проверьте восстановленные записи и миграцию через `psql` или отдельно поднятую изолированную копию. Автоматического переключения production на восстановленную БД нет.

Переключение после аварии — задача ответственного администратора: остановить запись, сверить последнюю подтверждённую копию, зафиксировать возможную потерю данных, проверить совместимость версии приложения, изменить целевую БД в **копии** production Compose и выполнить контрольный сценарий. Не подменяйте рабочую БД непроверенной копией и не делайте автоматический downgrade.

Для ежедневного резервирования можно настроить cron у пользователя с нужным доступом к Docker. Это пример задания на сервере, который вы добавляете самостоятельно:

```cron
0 3 * * * cd /opt/dentflow && /bin/bash scripts/backup.sh production >> /var/log/dentflow-backup.log 2>&1
```

03:00 здесь — часовой пояс самого сервера. Убедитесь, что пользователь может писать в указанный журнал, настроены его ротация и контроль ошибок. Сам код проекта не создаёт cron и не покупает хранилище.

## 10. Мониторинг

Проверьте состояние контейнеров, health endpoint, очередь и диск:

```bash
docker compose --env-file .env.production -f compose.production.yaml ps
docker compose --env-file .env.production -f compose.production.yaml logs --tail=100 backend worker
curl --fail https://app.example.ru/api/health
df -h
```

Нужны оповещения о недоступности health, росте failed/pending в очереди, истечении сертификата, заполнении диска и неуспешной резервной копии. В коде есть health checks и heartbeat worker в Redis, но внешняя система мониторинга и получатели оповещений требуют вашей настройки. Внешнему мониторингу не передавайте историю пациентов и секреты.

## 11. Telegram и AI

Базовый стенд работает без ключей. Не начинайте с подключения платных API. Сначала проверьте запись, затем следуйте TELEGRAM_SETUP.md и AI_CONFIGURATION.md.

Для Telegram нужен ваш бот от BotFather, `TELEGRAM_ENABLED=true`, token и slug клиники. Для внешнего AI нужны `AI_EXTERNAL_ENABLED=true`, соответствующие переменные и выбор провайдера в кабинете. Затраты возникают на стороне провайдера; код не обещает бесплатного коммерческого тарифа.

Для новой интеграции GigaChat проверьте тип своего аккаунта и актуальный маршрут подключения: подготовленный OAuth-адаптер не равен отдельному адаптеру Cloud.ru. Подробности и официальные источники находятся в AI_CONFIGURATION.md.

## 12. Обновления и необязательный ручной CD

Перед обновлением выполните backup. Для локального стенда после замены исходников используйте `docker compose up -d --build --wait`. Для production сначала проверяйте изменения миграций на изолированной копии.

Ручной CD из GitHub требует дополнительной настройки:

1. Код на сервере должен быть git checkout в `/opt/dentflow`, а не только распакованный архив. Настройте read-only deploy key для чтения приватного репозитория.
2. Пользователь развёртывания должен иметь SSH-доступ, доступ к Docker и владеть папкой.
3. В GitHub создайте environment `production` и требование ручного одобрения, если ваш тариф/репозиторий поддерживает эту возможность.
4. Задайте secrets `DEPLOY_HOST`, `DEPLOY_USER`, `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`. Последний содержит заранее проверенный ключ сервера, а не случайно принятый при подключении.
5. Дождитесь успешного CI нужного commit. Откройте Actions → «Развернуть утверждённый commit» → Run workflow и вставьте полный 40-символьный SHA.

Скрипт проверяет принадлежность commit ветке main, создаёт backup, собирает контейнеры, выполняет миграции и health checks. Он не откатывает БД автоматически при ошибке: совместимость схемы требует решения ответственного. Если ключи не заданы, эта возможность не работает и сервер никуда сам не публикуется.

## 13. Если что-то не получилось

| Что видно | Что сделать |
|---|---|
| `docker` не найден | Установить Docker, заново открыть терминал и проверить `docker --version`. |
| `Cannot connect to Docker daemon` | Открыть Docker Desktop и дождаться готовности; на сервере проверить сервис Docker. |
| `no configuration file provided` | Вы в другой папке. Перейдите туда, где лежит compose.yaml. |
| Не найден .env | Запустите start-скрипт либо `python3 scripts/configure.py`. Не переименовывайте образец в production без генерации секретов. |
| Порт 8080 занят | Остановите другую копию. Для другого порта измените одновременно HTTP_PORT, PUBLIC_URL и ALLOWED_ORIGINS в .env, затем пересоздайте контейнеры. |
| 502 Bad Gateway сразу после сборки | `docker compose ps` и `docker compose logs --tail=100 backend frontend`; дождаться Healthy или исправить показанную ошибку. |
| Сборка прервалась / нехватка памяти | Освободить диск, выделить Docker больше памяти; повторить сборку без удаления DB volumes. |
| Пароль PostgreSQL не подходит после редактирования .env | Пароль существующего volume не меняется от редактирования env. Верните прежнее значение либо измените роль БД штатной процедурой. Не удаляйте рабочий том. |
| 403 при сохранении | Проверьте Origin/ALLOWED_ORIGINS и роль. Owner управляет справочниками; Administrator имеет меньше прав. |
| Вход сразу исчезает на production | Используйте HTTPS, проверьте домен и Secure cookie. Не отключайте COOKIE_SECURE ради обхода. |
| Нет свободных слотов | Проверьте активность филиала/врача/услуги, связь врача с услугой, смену на нужный день, перерыв и будущую дату. |
| Запись не видна в календаре | Выберите дату визита и правильный филиал/врача; обновите данные. Проверьте, что пациент и администратор открыли один стенд. |
| «Мои записи» пусто в другом браузере | Сессии независимы. Совпадение телефона не подтверждает личность. Используйте исходный браузер или настроенный аккаунт пациента. |
| Не удаётся записаться дважды на одно время | Это ожидаемая защита. Выберите другой свободный интервал. |
| Telegram не отвечает | Проверить token, TELEGRAM_ENABLED, профиль telegram, slug, отсутствие второго polling/webhook и журнал сервиса. |
| AI отвечает шаблонно | В demo это ожидаемо. Внешняя модель ограниченно классифицирует административные запросы; свободная медицинская консультация не предусмотрена. |
| Заявка на сайте не пришла на email | Она сохраняется в Super Admin. Email-провайдер не подключён. |
| Виджет на другом домене не помнит сессию | Браузер может блокировать third-party cookies. Откройте чат отдельной вкладкой или настройте same-origin reverse proxy. |

При обращении за помощью достаточно прислать текст ошибки, команду и обезличенные последние строки нужного журнала. Не присылайте `.env`, токены, резервные копии и данные пациентов.

## 14. Признаки успешного первого запуска

Главная страница открывается, владелец клиники входит, пациент в другом окне создаёт запись, сотрудник видит её и CRM-лид, перенос отражается у пациента, занятой интервал повторно не предлагается. Эти действия важнее одного зелёного health endpoint.

Для commercial pilot отдельно завершаются проверка production на вашей инфраструктуре, живой тест Telegram/AI/МИС, резервирование и восстановление, юридическая оценка и организационные документы. Фактически выполненные проверки этого выпуска перечислены в TESTING.md.
