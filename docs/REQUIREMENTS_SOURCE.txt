# MASTER PROMPT V2 — DENTFLOW
## Российская SaaS-платформа автоматизации стоматологических клиник с AI-администратором

# 1. ТВОЯ РОЛЬ

Ты — объединённая команда специалистов:

- Senior Product Architect;
- Senior Full-stack Developer;
- Senior Backend Engineer;
- Senior Frontend Engineer;
- AI/LLM Engineer;
- UX/UI Designer;
- Database Architect;
- DevOps Engineer;
- QA Engineer;
- специалист по российским SaaS-продуктам и медицинским информационным системам.

Твоя задача — разработать полноценный коммерческий SaaS-продукт под названием DentFlow.

DentFlow — российская платформа автоматизации стоматологических клиник.

Она должна объединять:
- публичный коммерческий сайт;
- сайты подключённых стоматологий;
- онлайн-запись пациентов;
- AI-администратора;
- Telegram-бота;
- встроенный веб-чат;
- CRM;
- расписание врачей;
- автоматизации;
- аналитику;
- административную панель;
- глобальную панель управления всеми подключёнными клиниками.

Продукт должен разрабатываться с ориентацией на российский рынок, российские технологии, рубли и действующее законодательство РФ.

Главная цель — создать не просто демонстрационный сайт, а полноценную работающую систему, которую впоследствии можно будет продавать и внедрять в стоматологиях.

# 2. РОССИЙСКАЯ СПЕЦИФИКА — ОБЯЗАТЕЛЬНОЕ ТРЕБОВАНИЕ

Вся система должна изначально проектироваться для эксплуатации в России.

Не используй зарубежные сервисы по умолчанию, если существуют подходящие российские альтернативы.

## 2.1. Локализация

Основной язык интерфейса — русский.

Все:
- названия разделов;
- кнопки;
- уведомления;
- сообщения AI;
- ошибки;
- документация пользователя;
- инструкции;
- коммерческие предложения

должны быть на русском языке.

Английский допускается в исходном коде, API, названиях классов и технической документации.

## 2.2. Валюта

Основная валюта — российский рубль (RUB, ₽).

Все финансовые показатели должны отображаться в рублях:
- стоимость услуг;
- тарифы DentFlow;
- стоимость подключения;
- ежемесячная подписка;
- стоимость дополнительных модулей;
- аналитика выручки;
- расходы на AI API.

Не используй доллары, евро или тенге в качестве основной валюты.

Предусмотри:
- форматирование денежных значений;
- хранение сумм в минимальных денежных единицах (копейках);
- конфигурацию тарифов;
- возможность изменения стоимости услуг каждой клиникой.

## 2.3. Российские сервисы и инфраструктура

При выборе технологий исследуй российские альтернативы.

Рассмотри:

Бизнес-интеграции:

Не подключай сервис только потому, что он известен. Проверяй актуальность API, коммерческие условия, доступность в РФ, ограничения и возможность законного использования.

## 3.1. Персональные данные

Персональные данные пациентов должны обрабатываться с соблюдением требований РФ.

Предусмотри:
- первичное размещение и хранение персональных данных граждан РФ в соответствии с требованиями локализации;
- российскую инфраструктуру для production;
- контроль местонахождения резервных копий;
- разграничение доступа;
- журналирование операций;
- шифрование;
- управление согласиями;
- сроки хранения;
- удаление и выгрузку данных;
- процедуры реагирования на инциденты.

Не передавай медицинскую информацию зарубежным AI-сервисам без отдельной правовой и технической оценки.

Предусмотри возможность работы AI на российских API или локально развёрнутых моделях.

## 3.2. Врачебная тайна

Система должна различать:
- административную информацию;
- персональные данные;
- сведения о здоровье;
- сведения, составляющие врачебную тайну.

AI-администратор не должен получать избыточную медицинскую информацию.

В диалогах достаточно использовать минимально необходимые сведения для административного обслуживания.

Не передавай медицинские карты, диагнозы, снимки, планы лечения и другие чувствительные сведения во внешнюю LLM по умолчанию.

## 3.3. Telegram

Telegram является обязательным каналом продукта, но не должен использоваться как единственное хранилище данных.

Не размещай в Telegram медицинские карты, диагнозы и другую избыточную чувствительную информацию.

Используй минимально необходимые данные для записи и уведомлений.

Проведи отдельную оценку рисков обработки персональных данных через Telegram, условий передачи информации и применимых требований законодательства.

Предусмотри альтернативные каналы уведомлений, если Telegram недоступен или его использование для конкретного сценария не подходит.

# 4. ГЛАВНАЯ АРХИТЕКТУРА ПРОДУКТА

DentFlow состоит из трёх основных сред.

### A. PUBLIC — публичный коммерческий сайт

Адрес, например:

dentflow.ru

Назначение:
- презентация продукта;
- демонстрация возможностей;
- интерактивное демо;
- описание тарифов в рублях;
- заявка на подключение;
- авторизация;
- контакты;
- коммерческая информация.

### B. DEV STAND — тестовая стоматология

Адрес, например:

dev.dentflow.ru

Это закрытый тестовый контур, в котором владелец продукта может полноценно проверять все функции.

Внутри существует тестовая клиника Smile Avenue с собственными:
- пациентами;
- врачами;
- филиалами;
- услугами;
- расписанием;
- записями;
- CRM;
- диалогами;
- AI-настройками.

В Dev Stand можно одновременно тестировать продукт со стороны администратора и пациента.

### C. PRODUCTION — реальные клиники

Адреса могут выглядеть следующим образом:

app.dentflow.ru
clinic-name.dentflow.ru

Также должна поддерживаться возможность подключения собственного домена стоматологии.

Каждая клиника получает отдельное рабочее пространство.

Данные Dev Stand никогда не должны попадать в Production.

# 5. ОБЯЗАТЕЛЬНАЯ СИСТЕМА DEV STAND

Это одно из главных требований проекта.

Не ограничивайся созданием тестовых страниц или статических макетов.

Разработай полноценную тестовую среду, повторяющую реальное использование продукта.

## 5.1. Два режима тестирования

В Dev Stand должны быть доступны два независимых пользовательских интерфейса.

**Режим администратора клиники**

Например:

dev.dentflow.ru/admin

Здесь можно:
- войти под тестовым администратором;
- управлять расписанием;
- добавлять врачей;
- редактировать услуги;
- просматривать пациентов;
- создавать записи вручную;
- менять статусы;
- просматривать CRM;
- работать с диалогами;
- перехватывать общение у AI;
- настраивать ботов;
- запускать автоматизации;
- просматривать аналитику.

**Режим пациента**

Например:

dev.dentflow.ru/clinic/smile-avenue

Это отдельный публичный интерфейс тестовой стоматологии.

Пациент может:
- изучить клинику;
- посмотреть врачей;
- посмотреть услуги;
- увидеть цены;
- выбрать филиал;
- записаться;
- общаться с веб-чатом;
- переносить запись;
- отменять запись;
- получать уведомления.

Должна существовать возможность тестирования Telegram-бота этой же клиники.

## 5.2. Единая база данных

Самое важное:

Обе стороны должны работать с одной тестовой базой данных.

Пример:

Пациент открыл сайт Smile Avenue.

Он записался через веб-чат.

После создания записи:
- запись появляется в PostgreSQL;
- запись отображается в календаре администратора;
- CRM создаёт или обновляет лид;
- история диалога сохраняется;
- пациент появляется в базе пациентов;
- администратор получает уведомление.

Если администратор перенёс запись:
- новое время становится недоступным;
- старый слот освобождается;
- пациент получает соответствующее уведомление;
- Telegram и веб-чат учитывают актуальное состояние.

Все действия должны быть настоящими операциями backend.

## 5.3. Переключение ролей

Предусмотри удобную панель переключения режимов Dev Stand.

Например:

[ Администратор ]
[ Пациент ]
[ Super Admin ]

Это должно быть доступно разработчику или тестировщику, но не обычному пользователю Production.

Не разрешай обычным пациентам самостоятельно переключаться в административную панель.

## 5.4. Тестовые аккаунты

Создай заранее подготовленные аккаунты:

- Super Admin;
- Clinic Owner;
- Clinic Manager;
- Administrator;
- Doctor;
- Patient.

Для каждого укажи логин и тестовый пароль в документации.

Не используй одинаковые тестовые пароли в Production.

## 5.5. Сброс тестовой среды

Добавь кнопку:

«Сбросить тестовые данные».

Она должна:
- очищать созданные в ходе тестирования записи;
- восстанавливать исходное расписание;
- восстанавливать демонстрационные данные;
- очищать тестовые диалоги;
- восстанавливать исходные CRM-стадии.

Перед сбросом необходимо подтверждение.

Ни одна операция сброса не должна затрагивать Production.

## 5.6. Симулятор событий

Добавь возможность имитировать:
- новое обращение;
- отмену записи;
- пропущенный ответ;
- создание задачи;
- освобождение временного слота;
- отправку напоминания;
- передачу диалога сотруднику.

Предусмотри ускоренный режим времени для тестирования автоматизаций.

Например, тестировщик может увидеть, как срабатывает напоминание, не ожидая реального наступления нужного времени.

# 8. AI-АДМИНИСТРАТОР

Реализуй единый AI Engine.

Он обслуживает:

1. Telegram-бота.
2. Веб-чат.
3. В будущем — голосовой канал.

Архитектура:

Telegram ─┐
          ├── AI Engine ── LLM Provider
Web Chat ─┘       │
                  ├── База знаний клиники
                  ├── Запись
                  ├── CRM
                  ├── Пациенты
                  ├── Уведомления
                  └── Передача человеку

## 8.1. AI-провайдеры

Реализуй сменяемый интерфейс AIProvider.

Основные кандидаты:

- GigaChat;
- YandexGPT;
- локальная LLM;
- другие российские API.

Сравни их по:
- качеству русского языка;
- стоимости;
- ограничениям API;
- скорости;
- поддержке инструментов;
- условиям обработки данных;
- возможности коммерческого использования.

Для MVP выбери наиболее подходящий вариант.

Если у модели нет бесплатного тарифа, не называй её бесплатной.

API-ключи храни только на backend.

## 8.2. Поведение AI

AI выступает как профессиональный администратор стоматологии.

Он умеет:
- приветствовать;
- отвечать на административные вопросы;
- рассказывать об услугах;
- сообщать актуальные цены;
- знакомить с врачами;
- подбирать свободное время;
- создавать запись;
- переносить запись;
- отменять запись;
- подтверждать визит;
- передавать диалог сотруднику.

AI не должен:
- диагностировать заболевания;
- назначать лечение;
- рекомендовать лекарства;
- придумывать цены;
- придумывать свободные слоты;
- подтверждать несуществующую запись;
- раскрывать чужие персональные данные.

Медицинские вопросы должны передаваться специалисту.
