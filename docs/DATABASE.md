# База данных

## Форматы

- PostgreSQL в development/devstand/production. SQLite допускается только в APP_ENV=test.
- Идентификаторы — случайные UUID в строковом представлении.
- Деньги — целые копейки: 5 500 ₽ хранится как `550000`. Плавающая точка для хранения денег не используется.
- Время — timezone-aware UTC в БД и ISO 8601 на API. В интерфейсе клиники используется её часовой пояс, в демонстрации Europe/Moscow.
- Доступные интервалы рассчитываются на 180 дней вперёд, с шагом 15 минут, с учётом длительности услуги, смены и перерыва.

## Сущности

| Таблицы | Назначение |
|---|---|
| tenants | Клиники, slug, статус, бренд, часовой пояс |
| branches, doctors, services, doctor_services | Филиалы, врачи, прайс и доступные врачу услуги |
| schedules | Недельные рабочие смены и перерывы |
| users, auth_sessions | Учётные записи, роли, хеши паролей и токенов сессий |
| patients, visitor_patients | Пациенты и доказанная связь с сессией |
| appointments | Записи с ценой на момент создания, источником, временем и ключом повторного запроса |
| leads | CRM-воронка и поля сделки; отдельная дублирующая таблица deals в MVP не нужна |
| conversations, messages | Канал, режим AI/сотрудник, состояние сценария и история |
| channel_links | Одноразовые хешированные коды привязки каналов |
| tasks | Задачи, ответственные, сроки и ключи от дублей |
| notifications | Внутренние уведомления и очередь внешней доставки |
| automation_rules | Индивидуальные правила клиники |
| integrations | Честные статусы интеграций и ошибки |
| ai_settings, ai_usage | Настройки и статистика вызовов; неизвестная стоимость LLM — NULL |
| audit_logs, consent_records | Действия пользователей и история согласий |
| plans, subscriptions | Цены тарифов и лимиты; состояние оплаты DEMO |
| connection_requests | Заявки с публичного сайта DentFlow |

Роли и матрица разрешений заданы в коде, а не в изменяемых администратором таблицах roles/permissions. Это сознательное ограничение MVP: клиника не может самостоятельно повысить себе права платформы. Таблица Alembic хранит номер миграции отдельно.

Все записи клиники содержат tenant_id. Глобальные сущности — планы, заявки на подключение, auth_sessions и пользователи с отдельной глобальной ролью. Внешние ключи и индексы присутствуют; API дополнительно проверяет tenant связанных сущностей. Не считайте обычный внешний ключ эквивалентом RLS или составного ограничения tenant+id.

## Конфликты и повторные запросы

В PostgreSQL устанавливается расширение `btree_gist` и exclusion constraint на tenant, врача и пересечение временного диапазона. Активные состояния: scheduled, confirmed, completed. Отменённые и неявки не блокируют время. Создание и изменение записи используют одинаковую блокировку врача.

Уникальность `(tenant_id, idempotency_key)` защищает повторную отправку; сервер хеширует ключ вместе с проверенной идентичностью. Уникальные связи ограничивают дубли пациентов одной сессии и CRM-лидов. Телефон может повторяться у разных людей и не используется как глобальный уникальный ключ.

## Миграции

```bash
docker compose exec backend alembic current
docker compose exec backend alembic history
```

`0001_initial.py` содержит фиксированную схему выпуска, независимую от будущих ORM-моделей. Для следующих изменений создавайте новую миграцию и проверяйте её на копии БД. Не редактируйте применённую миграцию в работающем окружении. Разрушительный downgrade запрещён: восстановление выполняется из проверенной резервной копии по отдельной процедуре.

Для новой разработки:

```bash
alembic revision --autogenerate -m "describe_schema_change"
alembic upgrade head
```

Автогенерация требует ручной проверки, особенно для PostgreSQL constraints и преобразования существующих данных. Изменение схемы не должно автоматически запускать seed.

## Хранение и удаление

Сроки хранения определяются оператором с учётом назначения данных и договоров. В интерфейсе пациент может выгрузить административные данные и направить запрос на удаление. Запрос создаёт задачу ответственному и отключает рассылки; это не мгновенное уничтожение всей истории. Регламент должен охватывать рабочую БД, очередь, резервные копии и подрядчиков.

Резервные копии — PostgreSQL custom dump. Они не заменяют резервирование `.env.production`, сертификатов и конфигурации, которые хранятся отдельно в защищённом месте. Копия в той же VM не защищает от потери VM; нужен второй защищённый носитель в согласованном регионе РФ.
