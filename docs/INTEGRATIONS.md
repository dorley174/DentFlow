# Интеграции: что работает, что требует подключения

Актуальность исследования: **05.11.2026**. Наличие названия провайдера в интерфейсе означает возможность развития продукта только тогда, когда это прямо отмечено. Работа с настоящей внешней системой подтверждается отдельным испытанием на разрешенном тестовом аккаунте.

## 1. Статусы поставки

| Компонент | Статус | Что требуется от владельца |
| --- | --- | --- |
| Внутреннее расписание и MockMISAdapter | Рабочий контур на БД DentFlow; записи не отправляются во внешнюю МИС | Запустить проект по [DEPLOYMENT.md](DEPLOYMENT.md) |
| Веб-чат и алгоритмический AI Engine | Работают без платного LLM API; используют данные приложения | Проверить сквозной сценарий Dev Stand |
| Telegram | Код общего канала подготовлен; по умолчанию отключен; живой бот без вашего токена не проверен | Создать своего бота, включить тестовый канал, пройти [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md) |
| Yandex / GigaChat / локальный LLM | Подготовлены сменяемые адаптеры ограниченного классификатора намерений; реальные аккаунты, биллинг и доступность моделей не проверены | Настроить выбранного провайдера по [AI_CONFIGURATION.md](AI_CONFIGURATION.md) и испытать на синтетических данных |
| 1С:Медицина. Стоматологическая клиника | Исследована официальная API-спецификация; реальный адаптер — следующий этап | Получить разрешение клиники, актуальную версию и тестовый доступ |
| IDENT | Исследована документация интеграций; адаптер отсутствует | Согласовать поддерживаемый протокол и лицензионные условия с вендором |
| Инфодент / Инфоклиника.RU | Исследованы официальные возможности портала; адаптер отсутствует | Согласовать тарифные опции, доступ и условия обмена |
| Подписки/оплата | DEMO без денег, банковских карт и фискальных чеков | Для приема денег нужен отдельный платежный адаптер и договор |
| SMS, телефония, VK, MAX, электронная подпись, 1С:Бухгалтерия | План развития; исходящие подключения в поставку не включены | Выбрать провайдера и реализовать проверенный адаптер |

Демонстрационные уведомления внутри приложения не равны доставленным SMS или сообщениям настоящего мессенджера. Проверяйте статус конкретного канала и ошибку доставки, а не только факт создания записи в очереди.

## 2. Единый контракт МИС

`MISAdapter` отделяет сценарии клиники от протокола конкретного поставщика. Контракт включает:

```text
get_doctors()
get_services()
get_schedule()
get_available_slots()
create_appointment()
update_appointment()
cancel_appointment()
get_appointments()
```

Каждый вызов должен иметь доверенный контекст клиники. `tenant_id` берется из авторизованной сессии/маршрута и повторно проверяется backend; модель или пользовательский текст не определяют доступ к клинике.

MockMISAdapter использует собственные данные DentFlow. Это позволяет воспроизводить запись, занятый интервал, перенос и отмену до заключения договора с МИС. Он не имитирует успешное подтверждение внешней системы. За актуальность внутренней записи отвечает общая служба расписания и ее транзакции.

### Правила для будущего реального адаптера

1. Определить источник истины: после подключения внешней МИС финальное подтверждение времени должно опираться на ее результат.
2. Сопоставить врачей, услуги и филиалы через устойчивые внешние идентификаторы. Не сопоставлять только по отображаемому имени.
3. Зафиксировать часовой пояс, длительность, рабочие часы, перерывы и точность времени.
4. Перед созданием/переносом повторно проверить доступность; конфликт вернуть человеку понятным сообщением.
5. Использовать ключ идемпотентности либо журнал соответствий исходящих запросов. После таймаута создания сначала выяснить результат, а не бесконечно повторять POST.
6. Различать «запрос принят», «подтверждено МИС» и «нужна ручная проверка». Не показывать подтвержденный визит при неопределенном исходе.
7. Обрабатывать удаленного врача, изменившуюся цену, отключенный филиал и недоступную МИС.
8. Сохранять необходимые технические метаданные без ключей и полных медицинских ответов.

## 3. Первая реальная интеграция: 1С

Официальный сайт решения публикует [документацию API редакции 2.1](https://stoma1c.ru/api/). Страница ссылается на [OpenAPI YAML разработчика Helix-QA](https://raw.githubusercontent.com/Helix-QA/API/refs/heads/main/api_stoma1c.yaml). YAML прочитан при исследовании; внешний сервер клиники не вызывался.

| Задача DentFlow | Методы в прочитанной спецификации |
| --- | --- |
| Врачи для онлайн-записи | `GET /hs/api/v1/book_staff/{clinic_id}/` |
| Услуги для онлайн-записи | `GET /hs/api/v1/book_services/{clinic_id}/` |
| Доступные даты и интервалы | `GET /hs/api/v1/book_dates/{clinic_id}/`, `GET /hs/api/v1/book_times/{clinic_id}/` |
| Создать запись | `POST /hs/api/v1/book_record/{clinic_id}/` |
| Перенести запись | `PUT /hs/api/v1/change_record/{clinic_id}/` |
| Отменить запись | `DELETE /hs/api/v1/cancel_record/{clinic_id}/` |
| Получить записи | `GET /hs/api/v1/records/{clinic_id}/` |

Спецификация описывает ключ приложения в заголовке `apikey`, Basic Authentication для прямого доступа к базе и отдельные методы пользовательской авторизации. Конкретные права, поля и токены зависят от метода и схемы подключения. В примере сервера присутствует HTTP: для реальных данных необходимо согласовать защищенный HTTPS/VPN-маршрут. Указанный в спецификации демонстрационный адрес не является вашим сервером.

### Что получить от клиники и 1С-партнера

- Версию конфигурации и платформы, тип размещения и адрес опубликованного API.
- Подтверждение лицензий на платформу/конфигурацию, поддержку и нужные функции интеграции. Состав продукта описан на [сайте 1С](https://solutions.1c.ru/catalog/stoma/structure); наличие лицензии не равно разрешению любого обмена.
- Отдельную тестовую базу с вымышленными пациентами, ключи с минимальными правами и разрешенные IP-адреса.
- Ограничения частоты/параллелизма, SLA, контакты поддержки, правила обновления API и условия коммерческого использования.
- Схему филиалов, услуг и врачей; правила цен, льгот, длительности и статусов.
- Возможность получать изменения: webhook, опрос с отметкой изменения или иной механизм. Webhook в DentFlow для 1С не заявлен реализованным.

Размер оплаты, доступность общей sandbox и универсальные лимиты API не подтверждены открытой спецификацией. Их нельзя выдумывать или считать нулевыми.

### Приемка адаптера 1С

На стенде клиники выполнить: чтение справочников → получение слотов → создание → появление в 1С → одновременный конфликт → перенос → освобождение старого интервала → отмена → повторная доставка запроса → временная потеря связи → сверка результата. Только после этого менять статус интеграции на «подключена».

## 4. IDENT и Инфодент

**IDENT.** [Официальная база знаний](https://help.dent-it.ru/help/nastrojki-integraczij) описывает внешние сервисы и собственные сервисы клиники; для ряда сценариев требуется модуль «Маркетинг». Это подтверждает наличие поддерживаемого интеграционного механизма, но не доказывает доступность произвольного общедоступного REST API с любыми операциями. Запросить текущий протокол, разрешенные операции записи/изменения, права, версию, стоимость модулей и тестовую инсталляцию. Сторонние продукты, называющие себя «IDENT API», не подменяют документацию вендора.

**Инфодент.** [Smart Delta Systems](https://sdsys.ru/products/infoclinicaru/) описывает портал Инфоклиника.RU для пользователей Инфодент/Инфоклиника PRO. В числе тарифных опций указаны шлюз записи из внешних порталов и расширенная интеграция через API. Условия зависят от выбранной опции и поддерживаемого внешнего портала. Перед разработкой подтвердить возможность подключения DentFlow, получить спецификацию и проверить права на чтение/изменение записи. Универсальная прямая запись в локальную БД МИС не предполагается.

## 5. Платежи и учет

В качестве будущих вариантов рассматриваются российские эквайеры: [ЮKassa](https://yookassa.ru/developers), [Т-Банк](https://developer.tbank.ru/) и [Сбер](https://developers.sber.ru/). Конкретный эквайер в этой поставке не подключен; наличие ссылки — список кандидатов, а не подтверждение тарифа или доступного метода.

Платежный модуль должен хранить суммы в копейках, валюту RUB и внешний идентификатор платежа. Перед live-режимом реализовать подпись/проверку уведомлений, повторную обработку webhook, серверную сверку статуса, возвраты, изоляцию магазинов клиник и отдельно фискализацию. Секреты магазина хранить на backend; данные банковских карт в DentFlow не собирать.

СБП — вариант платежного сценария у выбранного провайдера. Поддержка СБП не включается одним названием в интерфейсе. Интеграция с 1С:Бухгалтерией потребует согласованного формата документов и правил сверки, а не общего доступа к БД пациентов.

## 6. Коммуникации

Telegram подключается только своим токеном. Официальный протокол: [Telegram Bot API](https://core.telegram.org/bots/api). Отдельно проверить допустимость канала по [LEGAL_COMPLIANCE.md](LEGAL_COMPLIANCE.md). Чужие bot token, идентификатор голосового агента и телефоны из прототипов не используются.

Для SMS, телефонии, VK и MAX сначала получить официальную спецификацию и коммерческие условия. Для каждого нового канала нужны: проверка отправителя, привязка к tenant, минимальный состав данных, контроль согласия/отказа, обработка доставки, ограничение повторов и переход к альтернативному каналу. В этой версии голосовой агент из SalesBrain не воспроизводится: голос — последующий модуль общего AI Engine.

## 7. Виджет на сайте клиники

Файл `frontend/public/widget.js` создает кнопку и окно чата через iframe. Полный сценарий чата использует cookie сессии. В этой поставке cookie имеет `SameSite=Lax`: при размещении DentFlow на другом сайте браузер не обязан передавать ее внутри iframe. Поэтому вставка одного скрипта на произвольный чужой домен не гарантирует рабочую авторизованную запись.

Для пилота можно открыть чат DentFlow в отдельной вкладке: тогда он работает как собственная страница. Для встроенного сценария разместите приложение через согласованный reverse proxy на домене клиники и проверьте маршруты, cookie, заголовки и идентификацию в целевых браузерах. Настройка внешнего DNS и такого proxy автоматически не выполняется. Переход на `SameSite=None` без отдельной модели сессий и проверки CSRF не является готовым исправлением.

Не передавайте в URL виджета имя, телефон или данные о здоровье. `clinic_slug` выбирает публичную страницу клиники, но не дает доступа к ее административной части. После встраивания отдельно проверить: открытие → согласие → создание записи → ее появление в CRM → повторное открытие чата → выход из сессии.

## 8. Как отличать подготовку от подключения

Запись в настройках или кнопка «Подключить» не должны заменять проверку. Для внешней интеграции храните проверяемую карточку: владелец договора, версия адаптера/API, дата последней проверки, разрешенные операции, тестовые результаты, источник данных, статус ключа без его значения, тип последней ошибки и ответственный.

Рекомендуемые состояния: `disabled` → `configured` → `testing` → `connected`; при сбое — `degraded`/`error`. Это предложение для развития реальных адаптеров. До live-приемки используйте явный статус «требуется настройка» или «планируется».
